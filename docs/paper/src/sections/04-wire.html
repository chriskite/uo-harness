The wire

Everything the harness knows and everything it does passes through one asyncio process on localhost. This chapter shows how the stock client was put on that wire, how the stream is decoded (including the day we spent decoding it wrong), and how agent packets are spliced in so the server sees one ordinary client while the client is quietly kept in step.

Why a proxy

The first commit (e937fba, 2026-09-27 21:47) was an anti-cheat research report, and it set one rule before any code existed: the Outlands client stays 100% stock. The Outlands build of ClassicUO is compiled to native code (NativeAOT), so that rule ruled out most of the obvious designs ().

A proxy sees what the client sees, and an injected packet is, on the wire, the same thing as a key press. The price is speaking the Outlands protocol perfectly in both directions. This chapter is about how the harness does that.

Getting in the middle

The plan assumed upstream ClassicUO's -ip/-port arguments. On 2026-09-28 the Outlands fork turned out to ignore them, and settings.json too. The game server's address arrives as a literal IP in the HTTPS login response, and play.uooutlands.com "does not exist in DNS at all" docs/INTERCEPTION.md, so there is no name to hijack either.

WinDivert is a signed Windows driver that lets a user-mode program intercept and rewrite IP packets. divert_nat.py is 88 lines of pydivert on top of it and has to run elevated.

So the redirect moved below the client, into the kernel. harness/divert_nat.py catches outbound TCP to port 2593, rewrites both addresses to 127.0.0.1, and remembers which server IP S each client source port P was dialling; a return rule undoes it. Rewriting only the destination failed silently, because Windows drops loopback-destination packets with a non-loopback source as martians. The proxy dials out from ports 25940–25960, which the filter excludes, so its own traffic doesn't loop.

The first NAT matched one server IP, 74.91.115.123. On 2026-09-30 at 22:14 the client went to 35.71.142.123 instead, around the proxy "with no error shown", and twelve minutes later to 52.223.17.219. By 22:29 the NAT diverted any IP on :2593 (d0c7eb9), and the proxy asks its lookup service on :25943 which IP the client meant, dials that, and drops connections the NAT doesn't know. Across the 69 session logs the upstream split 35 / 19 / 15 between the three addresses. No payload byte changes; the server sees the player's IP with a different source port, like any home router.

Ports: 2593 game listen; 25940–25960 upstream source ports; 25941 control (agent packets in); 25942 state (JSON out); 25943 NAT lookup. Full reference in .

Inside, harness/proxy.py is one asyncio process: 218 lines at Phase 1 (0663786), 1,087 now. A SessionTap per connection decodes both directions packet by packet, feeds the world model (), and logs every packet plus the raw wire, flushed on every call "so a killed proxy loses nothing". World-model exceptions are caught: "relay must survive any model bug".

Two ciphers, one of them a compressor

The two directions are obfuscated differently. Client to server (C2S): a 5-byte cleartext preamble, then every byte XORed with one per-session key, c_i = p_i \oplus S (we had first modelled a per-position keystream; "one byte explains everything"). Server to client (S2C): a 13-byte cleartext prelude carrying both keys, then every byte XORed with K and run through UO's standard static Huffman code.

prelude  ff 00 0d 00 00 00 00 00 00 00 0c K S    (K = S2C key, S = C2S key)
C2S      ef 00 00 00 0c | packets ^ S
S2C      prelude | per packet: Huffman(packet) FLUSH pad-to-byte, all ^ K

The S2C property everything later depends on: each server packet is compressed on its own and ends in the flush symbol, padded to a byte boundary, so one flush segment is exactly one packet. The proxy can forward a packet's original wire bytes, drop it, or substitute encode_packet(new) without touching the rest of the stream. Re-measured on session 20261001_191355, harness/uo/s2c.py decodes 1,298,764 raw bytes into 83,929 packets with no leftover bytes, and re-encoding reproduces the wire with 0 mismatches (compression ratio 0.683).

The phantom dialect

For the first day we didn't know that, and the decode we had looked fine. The Phase 1 proxy (0663786, 2026-09-28 12:09) started Huffman at byte 19 and applied no XOR. A static Huffman tree decodes any bit string, and garbage throws up a flush symbol every so often, so out came a steady supply of "packets"; a length table extended "by desync search" framed them "cleanly" for long runs. By evening there was a story: Outlands spoke a custom S2C dialect, with a "world-state stream" of ids 0x00/0x40/0x3F/0x52, one-off 13,155-byte and 30,627-byte "dumps" plus a recurring family of ~100-byte records, a MessagePack hypothesis, and a commit titled "World-state stream resolved (negative result)" (9265c57, 18:22). Movement analysis then explained the missing fastwalk-key packets as "swallowed by the desynced regions".

One wrong assumption (no XOR, Huffman from byte 19) produced a self-consistent-looking but false picture that survived for a day.

— docs/PROTOCOL.md, lessons

The correction came from the client. The decompiled NetClient.ProcessRecv XORs every received byte with a key at NetClient+0x71 (prelude byte 11) before DecompressBuffer; upstream ClassicUO has no such step. Commit 5eb2138 (2026-09-29 15:04) fixed the decoder. Ten minutes later 8cc2724, "garbage-decode artifacts removed", deleted the wire-derived table entries (0x00=106, 0x6F=76, 0x9E=65, 0xDC=15) and the old decoder, fixed nine world-model parser layouts against real packets, and reduced docs/WORLDSTATE.md to a supersession notice: "All of that was decode garbage." On the capture where the old proxy had framed 103 S2C packets with 4 desyncs, the test fixture now asserts 2,835.

Lesson

A decode that frames is not a decode that is right. The rule we adopted: "Accept a decode only if it reproduces known plaintext and frames every capture end-to-end under the client's own length table without per-id guesses." The cheap check that would have caught it on day one was to look for the player's serial or name in the S2C stream. Once the stream is decoded correctly, those appear everywhere.

A length table from the binary

UO packets are fixed-length by id or carry a big-endian u16 length at bytes 1–2, so framing needs a length table. We took it from the client's own packet table: 145 base entries, with protocol-version tiers on top. Twenty-two standard fixed-length ids carry Outlands values: against upstream, 19 of them are 1–16 bytes wider (0x6C target is 27 bytes, 0x08 drop 22), 0xEF is narrower (21 → 5), and 0x0B and 0xB9 keep their length.

The client pads what it sends to the same table, so C2S framing uses it too: C2S_OVERRIDES holds the 27 ids where Outlands differs from upstream. Until 2026-09-29 17:21 (f73f64e) the only override was 0x91, and a real 27-byte target framed as 19 bytes; "the rest of the captured target became an 0x00 'packet' of 106 bytes that swallowed the following client traffic". Re-framed offline with the current table, all 65 non-empty captured client streams (443,502 packets, 2026-09-28 → 10-05) frame end to end with 0 desyncs. Live, the proxy has logged no desync since f73f64e (47 sessions, ≈67 h); before that fix, two 09-28 targets were misframed without being flagged, because the live detector only sees implausible lengths. When it does fire, the proxy logs it and forwards a byte anyway, so the relay never stalls.

Injection discipline

An agent action enters as a plaintext packet on the control port: a u16be length prefix, the packet, and an OK or ERR <reason> reply. InjectionHub.inject applies the same order every time:

  1. Gate. AgentGate.block_reason() checks kill, pause, mandatory break and the 8 h/day budget (2ffb29a). Client traffic is never gated.
  2. Walk gate. For 0x02 walks, MoveAuthority.agent_walk_block checks pacing and in-flight steps (next subsection).
  3. Upstream write. The packet goes through exactly the client's path (same rewrite, log and XOR) and is spliced in between whole client packets, never inside one.
  4. Client-only fix-up. Only after the server write: a gump reply is followed by a fabricated gump close toward the client, and a target reply by a fabricated cursor cancel.

The packets come from harness/actions.py (527 lines), where "every builder returns the exact plaintext bytes a stock Outlands ClassicUO client would emit", with layouts from the decompiled NetClientExt.Send_* methods, checked against captures. The proxy never injects the ~1/s keepalive: it carries no timestamp, and its timing is left entirely to the client.

Decision, 2026-09-30

"Byte-correct packets weren't enough: the audit found sequences the client can't produce (a context menu without its click, replies with missing entries, a cursor answered twice, steps into walls…)." The rule since then: agent traffic reproduces what the stock client sends for the same UI gesture, including the packets that accompany it, and an action the client couldn't perform right now is refused rather than sent (37a2b00).

One walk ladder for two walkers

A walk is 7 bytes: 02 <dir|0x80 run> <seq> <key u32>. The server answers with 0x22 ConfirmWalk or 0x21 DenyWalk.

Movement caused the most trouble. The client and the agent both send 0x02 walks on one TCP stream. The server accepts a walk only if its sequence number is the next one expected and, for the first walk after the server arms a token, its fastwalk key matches that token, a field stock RunUO ignores but which "on Outlands it is alive". The sequence wraps 0xFF → 1, resets to 0 on a seed (login, honored resync, teleport) or a deny, and rewinds after a silent rejection. The token is whatever the server's latest 0xBF sub 1 seed or sub 2 push armed: login usually ends on 8 (a 5, 6, 7, 8 burst) and most re-arms carry 1, but the server also sends 2–13, so the proxy copies the value from the seed rather than assuming the constants of the 09-29 model (9e0f3bf). Two independent senders on that ladder desync each other, and they did, in several ways ().

Two stages rested on beliefs that the corrected decode disproved. We had read the frozen client as a server-side "behavioral gate on walk trains"; with the server's packets visible, session 142237 showed all 12 agent walks confirmed while the client drew nothing. "The lockout was 100% client-side": the client freezes when it gets a 0x22 for a step it never took. And fix B needed the S2C stream editable packet by packet, which the phantom had made look impossible. Fix B and the decode correction landed in the same commit.

The current design lives in MoveAuthority. Every walk from either sender gets pkt[2] = next_seq on one ladder; the first walk after a seed carries the armed token, and the client's leftover copy is zeroed once "so the server never sees a spent token". The server's confirm for an agent step is hidden from the client and replaced by a fabricated 0x21 DenyWalk at the tracked server-true position. The client's handler resets its walker and calls SetInWorldTile: a teleport-in-place it accepts without complaint. (A fabricated self 0x20 would have been simpler, but the V10 handler ignores position for the player.) Client confirms are rewritten back to the client's own sequence. A walk unconfirmed after 3 s counts as rejected and the ladder rewinds; three rejections in a row stall agent walking; at most 5 steps are in flight, the stock client's limit.

Re-anchoring only after quiet (the 16:08 design) had a visible cost. During long agent walks the client's picture lagged a median of 10 tiles (max 53) behind the character, so it dropped mobiles it thought out of range and closed their status bars within 10 ms of the click: 93% of the time during agent walking, against 1–5% in human sessions, "a per-mobile signature a server log sees directly". A11 re-anchors on every hidden confirm and brought that to 0.3% (6 of 2,072). Its own side effect: each re-anchor re-fired the client's Auto Open Doors and Auto Open Corpses, so both were switched off and the Mover opens doors itself.

Two views of one session

The server and the client thus see different sessions on purpose ().

Target cursors needed the most care. When the server raises a cursor (a spell, a hatchet) and the agent answers it, the client's cursor is still up, and a later click would send a second reply to a cursor the server already consumed: "a stock client can't reply to one cursor twice". The 09-30 audit found exactly that 4 times in one session. Cancelling only the client's copy is not enough, because the stock client answers a cancel with its own C2S cancel. So the proxy sends the client the server's exact cancel, marks the cursor id spent, and drops the client's reply to it (). That is the only client packet the current proxy drops; a resync-suppression test on the morning of 09-29 once dropped a client resync.

It balances exactly. Across all 69 logs there are 5,688 fabricated cancels and 5,688 dropped client replies, a 1:1 match, mirrored in the memory store's event table. In the 20261001_191355 audit, all 479 agent target answers went to live server cursors and 0 client 0x6C replies were relayed.

Three quarters of that (55,615) were walks; then come 0x06 double-clicks (6,256) and 0x6C targets (5,824). From 10-01 the two counts match to within 4 a day (the extra re-anchors are timer re-anchors after rejections and late confirms).

Walking is fast now. The median time from an agent walk to the server's confirm is 46–63 ms across the three big sessions, about one network round trip (keepalive RTT medians 46–66 ms on the same sessions), i.e. the server confirms at once. The maxima of 3.2–3.5 s are server pauses (on 10-01, documented world saves). They exceed the 3 s confirm timeout, which was raised from the 1.5 s first tried after 2.0–2.3 s hitches, so such a walk is first counted as rejected and then recovered by the 5 s late-confirm window. Above the proxy's floors, the Mover adds the stock held-key cadence plus 3–15 ms of jitter, giving a median gap of 0.248 s on foot and 0.117 s mounted (6917539). A human running on foot has a median of about 0.200 s.
