Memory

Everything the harness sees, does and concludes goes into one SQLite file. Deterministic code reads it to walk, chop and plan; the LLM reads a small, curated part of it through a ranked search. The store also serves as the message bus, the analytics warehouse, the training set and this paper's data source. This chapter covers how it is built, how each part is read, and what we can and cannot say about how well it works.

Three memories and the line between them

Three different things in this project could be called memory (). The coding agents that built the harness remember through the git repository. The harness remembers through its runtime store, harness/data/harness.db. The Seer, the LLM that supervises the harness (), also has its context window, which lasts one session and gets compacted. This chapter is mostly about the second, but the boundaries between the three were deliberate design decisions.

The line between the first two came from a clarification by the owner. Rule 0 orders every coding session to "record and commit engineering knowledge". On 2026-09-29, when the store was built, the rule gained a second paragraph: it "does NOT cover the harness's own runtime memory … game state, what the agent learned while playing (walk/harvest memory, episodes, hazard stats), event logs and captures of its play" AGENTS.md:9; 7a3e26f. The repository keeps how the memory works (the code, docs/MEMORY.md) plus the captures that tests cite as evidence; the contents stay in a gitignored file. This keeps a 289 MB, fast-changing, partly personal data set out of a repository that agents read at the start of every session, and it means that a new checkout knows how to remember but has no memories. It is also why moving to a second computer needed its own tool ().

The line between the store and the context window is just as deliberate. A Seer's context does not outlive its session, and on 10-05 alone six numbered Seers played one after another (). Whatever one Seer should know about the previous one's work therefore has to be in the store. A new Seer starts with ctl status, the open junctures and ctl know brief, and the prompt makes it read and follow every pinned entry first docs/OVERSEER.md:376-379. Pinning was added on 10-04 at the owner's request because importance alone could not guarantee recall: 26 standing candidates were competing for the brief's 12 slots. The first pinned entry, #4079, is the procedure for using the guild's rune library 71e4207. How often the Seer's own context was compacted during shifts was not measured inferred: the compaction figures in are for the coding sessions.

One store, many roles

The store is SQLite in WAL mode with synchronous=NORMAL. It replaced three JSON/JSONL files (walk memory, harvest memory, lumber episodes) in one cut-over at 22:06 on 2026-09-29, the same evening as the map 7a3e26f.

Decision

SQLite, because it is durable (the WAL survives crashes), indexed, in the standard library, and lets the proxy, runners, viz, ctl, overseer and Telegram bridge all read concurrently while writers take turns (one writer at a time). Rejected: JSON files (walkmem.json "was 2D, facet-less and rewritten whole"), Postgres ("needs a service"), DuckDB ("analytics-first, not in the stdlib, single-writer file lock").

Schema growth without migrations. Every connection runs the whole schema as CREATE … IF NOT EXISTS and then writes schema_version harness/memory.py:166-174. A new table therefore appears the first time any process opens the store; there are no migration scripts. The schema went from v1 to v5 in 25 hours. After that, three more additions (guard_points, knowledge_vec, two time indexes) came without a version bump (). Columns were never altered. New fields went into JSON data columns, which is how a lumber trip row reached 44 keys without a schema change. One side effect: opening the store is itself a write. Anything that must not write (the backups, the Laya data builder and every query in this paper) uses a separate mode=ro connection.

The write path. The proxy is the heaviest writer and the one that must never stall, because it relays the game connection. Its MemoryWriter is built so that "the relay never waits on disk": record() puts the event envelope on an in-process queue and returns. A daemon thread with its own connection inserts each event, derives walk rows from it in the same transaction, and commits every 0.25 s or every 500 rows, whichever comes first harness/memory.py:512-586. Events are keyed on (session, seq) and inserted with INSERT OR IGNORE, so replaying a capture twice is harmless. A failed insert is counted in errors and skipped; nothing retries it. Runners write through the Memory class on their own connection and commit after every call, a harvest attempt or a trip row at a time. That is cheap at their rate, a few rows a minute.

Concurrency. WAL gives one writer at a time and any number of readers on the same host. Writers wait up to 30 s for the lock harness/memory.py:168. The store has six kinds of writer (proxy, runners, ctl, the Telegram bridge, the Discord pipeline, the capture ingester) and more readers. We found no record of a lock timeout in normal operation inferred: the docs mention "database is locked" only for the handoff's deliberate writer check, and the writer's error counter is not persisted. "Same host" turned out to be the real constraint, and it is why the store could not live on the NAS ().

Episodic memory: what happened

The event log. Every event the proxy's state port emits is stored as an envelope: session, sequence number, time, origin (world for the world model, proxy for the proxy's own movement and control logic), event name and a JSON payload. Here is a real row, a server-confirmed step north at 19:00:10 on 10-05, during a lumber trip to the spot witcher_23, and the walk row it created:

events     (session 66, seq 365982, t 1791244810.477, origin 'proxy', ev 'step',
            data {"ev": "step", "from": [1681, 660], "to": [1681, 659], "z": 1})
walk_moves (facet 0, x 1681, y 660, z 1, dir 0, ok 1)  n = 1, first_t = last_t = t

A second confirmation of the same move would only raise n and last_t harness/memory.py:178-205. The log holds 64 event kinds. It is not curated, and the volumes show it: the server's keepalives are the largest kind, 488,223 rows or 29% of the log; items coming into view (item_seen, 364,582), deletes (116,249) and animations (101,551) follow. By payload bytes, item_seen (22%) leads keepalives (20%). The payloads total 128 MB of JSON, about 76 bytes per event SELECT ev, count(*), sum(length(data)) FROM events WHERE t < 20:30 GROUP BY ev. We kept everything because nobody could say in advance which events would matter. That bet paid off several times (below).

Sessions and captures. The 69 sessions are 44 live proxy sessions and 25 older captures. python harness/memory.py ingest replays a capture through the proxy's own SessionTap and writes the rows a live session would have written; all 25 captures (70.6k events) took 7.7 s docs/MEMORY.md "Who writes what". Since live and replayed sessions go through the same code, the raw captures in logs/ are a second, lossless episodic memory, the bytes on the wire. Ten of them are committed as test fixtures, the only runtime data allowed in git under Rule 0 git ls-files logs; AGENTS.md:9.

Trip rows. episodes holds one JSON row per runner trip or hunt visit: 63 lumber rows and 36 hunt rows at the snapshot. The latest lumber row has 44 keys: spot, outcome and why, phase times (harvest, to_room, convert, store), walking and chopping seconds, steps and blocked moves, skill before and after, hatchet and its uses, travel legs, supplies, players seen, captchas, escapes, attempts, successes and logs. On average a lumber row is 1.6 KB. The row is written in a finally block, so a trip that ends in an exception still leaves one harness/loop_lumber.py:3179-3180, 3230-3242 at HEAD. That was not always so. Until 2026-10-02 only trips that reached the bank were recorded, and "leaving those out flattered exactly the spots where trips get cut short: of the 2026-10-02 Terran and Corpse Creek runs only the trips that banked were recorded" docs/LUMBER_LOOP.md:1219-1222. The size of that bias shows in the rows since: of the 45 lumber rows that carry an outcome, 30 are aborted, against 15 banked or stored. A process kill still writes nothing.

Everything else that happened. job_events (1,370 rows, 19 kinds) records facts that are not trips: Smart Harvest stands (452), kills (229) and loot (213) on hunts, speech holds and clears, flights, player-killer sightings, recalls, monster sightings and hits, thefts and deaths. junctures (314) and chat (2,855) are the overseer bus and the conversation; covers them.

Learned memory read by code, not by the model

Most of what the harness learns is never shown to the LLM. The runners and the planner read the store directly, with plain SQL and no prompt, so the system gets better from its own records without any model in the loop. lists each piece of learned memory, where it is read and what it changes.

Walk evidence. walk_moves is keyed on (facet, x, y, z, direction, ok) with a hit count and first and last times. The projection the planner sees treats a move as blocked "only while its latest deny is newer than its latest confirm", because "doors and mobiles block only for a while" harness/memory.py:220-235. The human's walking teaches it as well as the agent's. Until the 3-D map arrived on the evening of 09-29, this was the only planner the harness had, and it failed the first time the character came out on an upper floor (). Today the map planner () does not consult walk memory at all. The table still serves the rental rooms on facet 3, the viz's walk layer, and evidence: the map's walk rules were accepted because all 1,249 server-confirmed moves then in the table came out walkable.

Harvest memory and the planner. A tree tile that ran dry or proved unreachable is skipped until the regrowth window has passed. The window itself is learned: lumber_opt.regrowth pairs every depleted attempt with the next attempt on the same tree and fits P(regrown | gap) isotonically, giving 65 minutes at the snapshot (). Each ctl lumber plan call reads every lumber trip row, every sighting, escape, theft and death, and the whole attempt table, then turns them into the posteriors of . At this scale, a few thousand rows, a full read costs less than keeping a cache in sync. Because every new row is evidence for the next plan, the quality of the records matters as much as the model. The survivorship fix above is one example; another is the rule that the Seer runs the planner's command "verbatim", because "hand-picked arguments spoil the data" ().

Recorded once, used later. Several consumers appeared after the data they read. guard_points came on 10-02, and python harness/guards.py backfill filled it by replaying the event log for the guard message, including events recorded before the table existed docs/MEMORY.md, guard_points row. Hatchet wear is read from speech_heard events that were stored for the journal. Laya's training set drew real player lines from the same events (). The meta table shows the opposite tendency: small learned facts (a character's books, landings that put us somewhere else, its pet) went in as JSON blobs under a key because no table fit them. That was quick to build but invisible to the schema.

Semantic memory for the LLM: ctl know

The other tables record events. knowledge holds what the agent concluded: game knowledge and its dealings with players and the owner, kept across shifts docs/MEMORY.md "Knowledge". It is the only part of the store the LLM reads as memory, and it is built like a small agent-memory system: typed entries, provenance on each one, versioning instead of overwrites, and ranked hybrid retrieval. An example, the resurrection procedure as it stood at the snapshot:

#4095  procedure  "resurrection"   source user, confidence 0.9, importance 9, tags death healer
  "On death there's no gump and no Young transport; the ghost stays put and the corpse takes
   the gold. Walk the ghost to a healer (…): the Resurrection gump (Accept 1 / Decline 2) opens
   within 2 tiles; stand still, then ctl act gump <serial> 1; …"
  supersedes #4094 (10-05 11:07), which superseded #13 (09-30 10:38, from the Young demos)

Data model. Each entry has a kind (fact, procedure, episode, preference for a standing directive of the owner's, insight for a lesson drawn from episodes), a topic, the content, tags, the entities it is about, and optionally a location (facet, x, y). Provenance is a source_type plus a source_ref (capture tag, chat or juncture id, URL). Confidence starts at a prior for the source: user 0.95, observed 0.9, doc 0.8, wiki 0.7, community 0.6, inferred 0.5 harness/knowledge.py:54. The writer sets an importance from 1 to 10 ("how much it matters if forgotten"). status is active, superseded or retracted, and supersede links form a version chain. access_count and last_access_t record retrieval. A tag char:<name> scopes an entry to one character, and the tag pinned makes it a standing memory.

Write discipline. Writers call ctl know add; code enforces the hygiene. If the normalised content hashes the same as an active entry's, or it shares ≥ 85% of its words with an active entry on the same topic, the write confirms that entry instead of adding a copy: confirmations go up by one, and confidence closes half the gap to 1, capped at the new evidence's source prior plus 0.05 harness/knowledge.py:140-191, 247-259. Every write returns up to three related entries (same topic or ≥ 35% word overlap), so the writer sees a likely contradiction while it is still one entry. A content change creates a new version that supersedes the old one, and a wrong entry is retracted with a reason; nothing is deleted. The prompt adds the rest: write "one self-contained statement that names the item, place, NPC or spot … search finds entries by their topic and content, so an entry that leans on context you had at the time is lost", label guesses --source inferred, and scope character-specific entries docs/OVERSEER.md:457-472.

Retrieval. Word search came first. On 09-30 embeddings were left out on purpose: "FTS5 + stemming is enough at this size and needs no model or network" c0bf3ce:docs/MEMORY.md. Three days later it had stopped being enough: word search missed paraphrases ("my character died" against "resurrection"), and the table had just taken in 820 Discord facts. Relevance became hybrid on 10-03 f55bc2c; docs/PLAN.md:686-707. A query is embedded with bge-small-en-v1.5 (384 dimensions, local, on the GPU) and compared by cosine with a vector of "topic: content" for every active entry. Separately, FTS5 ranks entries by BM25, with the topic weighted 3× and tags and entities 2×. The top 60 of each ranking are fused by reciprocal rank and scaled so the best candidate gets 1:

\text{rel}(e) = \frac{f(e)}{\max_{e'} f(e')}, \qquad f(e) = \sum_{r \in \{\text{cos},\,\text{BM25}\}} \frac{1}{60 + \text{rank}_r(e)}

Candidates are then reranked in the style of Generative Agents harness/knowledge.py:351-374:

\text{score} = \text{rel} + 0.4\,e^{-\ln 2\cdot \text{age}_d/14} + 0.5\,\tfrac{\text{importance}}{10} + 0.3\,\text{conf} + 0.6\,\max\!\left(0,\,1-\tfrac{d_\infty}{40}\right)

Recency halves every 14 days, and its age counts from the later of the last update and the last access, so retrieving an entry also makes it recent. Importance and confidence are the write-time values. Nearness applies only when the caller passes a position: d_\infty is the Chebyshev distance in tiles to the entry's location on the same facet, and the bonus fades to zero at 40 tiles. Every returned result counts as an access. Vectors live in knowledge_vec, keyed by a SHA-1 of the model name and the text, and the searcher embeds whatever changed before each search. Writers (the proxy, ctl know add, the Discord promoter) therefore never load the model. A sidecar vector database was rejected as "another file to back up and keep in sync for ~1k rows that numpy scans in microseconds" docs/PLAN.md:696-700. On a copy of the store, loading the model took 0.56 s and a hybrid search over 4,107 vectors 0.18 s on the desktop GPU; a ctl call costs about 1.5 s in all, mostly process start and model load measured on the copy; docs/PLAN.md:704. When the running Python lacks the embedder, recall falls back to BM25 and says so (recall: words).

The brief. ctl know brief builds the start-of-shift context without a query string. It returns three disjoint lists for the character being played: pinned (every pinned entry, in full, uncapped), standing (unlocated procedures and preferences of importance ≥ 7, capped at 12), and relevant (entries within 40 tiles, entries whose entities name a mobile in view, and entries whose cosine with the current intent, open junctures or task is at least 0.65) harness/knowledge.py:423-470. The 0.65 floor and the exact-name match replaced a looser design on 10-04. The old brief embedded one query made of every mobile's label, and at the guild house a stablemaster's label called up the Shelter Island stablemaster's prices at cosine 0.70 docs/MEMORY.md "Situational brief".

Calibration. search has no similarity floor: it always returns its top results. The prompt therefore teaches the Seer to read the cosine, "around 0.6 and up is on topic; below ~0.55 is noise" docs/OVERSEER.md:438-441. On a copy of the store, "what is the capital of France" peaks at cosine 0.54, and the pinned guild-library procedure (importance 8) still comes back first.

What the store holds. At the snapshot the table has 4,107 rows: 3,715 active, 366 superseded and 26 retracted (). It is mostly imported. 3,388 of the active entries (91%) are community facts from the Discord pipeline and 173 more are official ones stored as doc. The Seer's own observations number 116, the owner's directives and corrections 27. The two groups also differ in the ranking inputs (): Discord facts are capped at importance 6, almost all sit at 2–4, and their confidence is 0.65–0.85; the Seer's and owner's entries sit mostly at 5–9 with confidence 0.85–0.95. All 62 located entries are the Seer's or the owner's, so the nearness term helps only them. 49 entries are scoped to a character.

A worked example. At 20:21 on 10-05 a Seer playing Outland Dan asked its memory "finish a lumber trip by hand convert logs to boards" (chat #2855). shows the ten results the Seer got back, with the score taken apart term by term. We re-ran the same search on a copy of the store with the clock set to that moment.

The example shows three properties of the ranking that we had not designed for. First, fusion compresses relevance. Ranked first in both lists, an entry gets 2/61; tenth in both, 2/70, which scales to 0.87; first in only one list, 0.5. All ten results here have rel between 0.74 and 1.0, while the prior terms (rec + imp + conf) differ by up to 0.3 among them. In the full re-run, across the 60 entries ranked, relevance spanned 0.26–1.0 and the priors 0.67–1.14. The most relevant entry (#118, rel 1.0, the highest cosine) came fourth, behind two entries with higher importance.

Second, the priors favour the store's own entries. Importance, confidence and location are all higher for what the Seer and the owner wrote, so imported facts lose ties. The third most similar entry overall is a community fact (cosine 0.748) that ranks 17th. In a re-run of "my character died, how do I come back", the most similar entry is a community procedure for resurrection after dying in the wilderness (cosine 0.759). It ranks 14th, behind the Seer's account of Outland Dan's death at Wintertop and the owner's resurrection procedure. For a Seer that is supposed to treat Discord facts as "leads, not truth", this bias may be what we want; it was never measured.

Third, scope is enforced in one path only. brief drops entries tagged for other characters; search does not harness/knowledge.py:311-349 vs 440-466. So the top two answers to a question about Outland Dan's trip were Hackworth's lumber goal and banking routine from 10-01, both on Shelter Island. The other eight came from the first two days of play. The Seer got a stale, partly foreign context and had to filter it by reading.

How it was used. Every ctl know call except stats also posts a chat row of kind memory, so usage is on record. By the snapshot there were 359 such rows: 149 adds, 135 searches, 29 briefs, 19 updates, 18 gets, 8 confirms and 1 pin SELECT json_extract(data, '$.op'), count(*) FROM chat WHERE kind = 'memory'. These include calls coding agents made while testing, which we cannot separate. Only 9 entries have ever been confirmed (5 observed, 2 community, 2 doc). The Seer retracted one entry, its own duplicate, and no Discord fact. The design assumed the Seer would confirm or retract community leads as play tested them; in practice that loop barely ran.

Finding

There was no retrieval evaluation. No labelled set of questions with expected entries exists, so we report no precision or recall figures. The unit tests check the mechanics on toy entries (deduplication, versions, the location boost, and a fake three-axis embedder under which "dying" meets "resurrect") harness/test_knowledge.py. The only quality evidence is what the logs show: the calibration probe, the cases above and the access counts. The 10-04 changes to the brief (the 0.65 floor, character scoping) came from the owner's complaint that most of a brief did not apply to Outland Dan and from one bad live match, not from a metric.

Importing community knowledge

Most of the knowledge table was imported. A read-only capture records the pages the Outlands Discord web app itself loads while scrolling, at a reader's pace: about 10k messages an hour 22a8047, 97k in all docs/PLAN.md:93. Raw chat is "unreliable: jokes, outdated patch info, wrong answers", so only vetted facts reach the Seer (). The pipeline is memory ingestion with provenance: each promoted entry carries source_type community (or doc for official posts), the tag discord and a reference to its fact id and a jump link to the message.

A claim survives only if it cites message ids and quotes one verbatim. The adjudicating model proposes a fact and verdict, but code recounts independent authors: official needs an official-channel claim, consensus at least two supporting authors outnumbering dissent, else single_source or disputed, and confidence is "a fixed function of the final verdict … not the model's opinion". Promotions are capped at importance 6, below standing-brief level. The first run (10-03) promoted 820 facts for $26.26 over 761 calls; the rebuild (10-04) took 20,053 grounded claims to 14,016 clusters and 3,561 active entries for $71.11 over 1,953 calls, list-price estimates on the owner's subscription.

The pipeline also keeps the store consistent over re-runs. Promotion state is kept per target database, so a trial run into a copy never mixes up the real store's ids. An entry the Seer retracted or superseded is never re-added, even under new wording. When a fact's verdict drops, the pipeline retracts the entry only if it added it and nobody has confirmed it since docs/PLAN.md:668-674. At the snapshot the 3,561 are still there: 3,388 consensus facts as community and 173 official ones as doc. The 3,102 rows of the 10-04 promotion arrived between 12:00 and 12:45 and grew the store by 10 MB ().

Memory as a bus and as training data

A durable bus. The Seer, the runners, the viz and the Telegram bridge never talk to each other directly. Runners post junctures, everyone posts chat rows, and meta holds the running tasks, a heartbeat and one cursor per consumer (). Since there are no queues, only rows and cursors, any party can restart alone, and every message stays on record. That is how the paper can report median acknowledgement times per juncture kind, and how this chapter can count memory lookups.

Labelled data. The store doubles as a data set. Laya's fine-tuning set took its 221 real player lines from speech_heard events, read through a mode=ro connection harness/triage_data.py:23-25, 151-153 (). Every speech hold that ends in a clear writes a speech_clear job event with the lines, their context, Laya's check and direct scores and how long the hold lasted. At the snapshot there were 53 such rows, every one with a Laya score, and each is a real verdict on a real line. They are labels waiting for a use: the current training set does not read them (). The planner's training data is the trip rows. Ten committed captures are test fixtures, the viz replays captures through the same ReplayDriver as memory.py ingest, and most charts in this paper are read-only queries over the store.

Operating it: backups, handoff, growth, cost

Since 2026-10-01 an hourly scheduled task copies the store to the NAS with the SQLite online backup API from a mode=ro connection: it never checkpoints or writes the live file, yet includes the WAL's rows. The copy is switched to a rollback journal so it stands alone, checked, gzipped and deduplicated by sha256. That day's restore drill matched all 11 tables row for row (247,502 events) docs/NOTES.md "Backups".

On 2026-10-04 the owner wanted to "play on a desktop for a while and find its changes on the laptop afterwards." dbhandoff.py keeps one holder and numbered generations on the NAS: push uploads a verified snapshot as generation N+1 and releases it; pull installs it and records the holder. Two checks make it safe. The writer check: PRAGMA journal_mode=DELETE on a WAL store succeeds only for the sole connection, so push refuses while anything else has the store open, even a read-only reader. The fork check: a per-table fingerprint (row count plus sha256 over rows in rowid order; 1.15 M events in 1.9 s) is compared with the one recorded at the last sync, so a pull never silently overwrites local changes. The very first desktop pull refused, "this store has unsynced changes", because a harness command had created an empty database first da0bcb9. Opening the store writes to it, so the empty file already counted as local history.

Lesson

A live store on the network share was rejected because WAL needs every connection on one host; sync clients (OneDrive, Syncthing) were rejected because they would copy harness.db and its -wal at different moments and tear the store. Merging diverged stores would collide autoincrement ids in eight tables. In the plan's words: "Preventing forks is cheap and merging isn't, so forks are refused."

Growth. shows how the store filled. Event volume follows time in game: 532,419 events on 10-03, the busiest day, and 91,315 on 10-04, the day of the move to the desktop. The hourly backups show the file growing from 52 MB on 10-01 at 23:00 to 282 MB at 20:00 on 10-05, about 6.5 MB per hour between 10:00 and 20:00 on 10-05. Gzip shrinks it 5.4 times. Knowledge grew in two steps, the two Discord promotions; everything the Seer wrote itself fits in a few dozen rows a day.

Reading a live store. Every database number in this paper was read from a store a runner was still writing (). Three rules made that safe. Connect with mode=ro, because the harness's own connect() writes the schema on open. For anything heavier than a count, take a consistent copy with the backup API first. And cut every count at a timestamp rather than "now". The knowledge searches in this chapter ran on such a copy, because a real ctl know search updates access statistics and would have changed what it measured.

Cost. Storage: 289 MB for six days, 128 MB of it the JSON payloads of events, a fifth of those keepalives. Compute: local embedding, a fraction of a second per search plus the model load. Money: the two Discord runs, $26.26 and $71.11 at list price on a subscription. The rest is engineering time. memory.py, knowledge.py, embedder.py, dbhandoff.py and backup.py come to about 2,000 lines, and docs/MEMORY.md was touched by 25 commits ().

Lessons for AI engineers

1. Keep one append-only record and derive the rest

We stored every event before we knew what we would need. Guard points were backfilled from events recorded before their table existed, hatchet wear was read from journal events, Laya's real negatives came from speech events, and this paper is mostly a set of queries over the same file. The price was a log in which 29% of rows are keepalives. A single SQLite file with IF NOT EXISTS schema growth and JSON payload columns took seven schema additions in six days without a migration.

2. Record failures with the same care as successes

A trip row written only on success made the dangerous spots look good. After the row moved into finally, 30 of the 45 trips that recorded an outcome turned out to be aborted ones. When code learns from its own history, the logging path is part of the model.

3. Check the scale of every term in a reranker

Reciprocal-rank fusion squeezes the relevance of good candidates into a narrow band (0.5–1.0), and additive priors for importance, confidence and recency then decide the order. In our store this demoted imported facts systematically and put an earlier character's preferences first. Recency that counts from the last access also feeds on itself. None of this is visible without taking scores apart on real queries, and a small labelled query set would have been cheaper than finding it in a paper.

4. Enforce provenance in code; give curation an owner

The Discord import worked because code, not the model, decided what counted as evidence: substring grounding, author recounts, confidence fixed by verdict, an importance cap. The curation loop that was left to the agent, confirming or retracting community leads as play tested them, hardly ran: 2 confirmations, no retractions, and 93% of imported facts never retrieved. A memory that only grows needs a process that prunes it.

5. Prefer ground truth you can read over memory you have to learn

Walk memory was the harness's first planner and failed the first time the character came out upstairs. The client's own map files replaced it within an hour. Learned memory earns its place where nothing can be read (regrowth, yields, hazards, prices, who our pet is), and the LLM's memory where judgement is needed. Neither should stand in for data the system can read directly.
